# Standard Checklists

This document defines the standard checklists that should exist for every feature to ensure consistent quality and compliance.

## Checklist Types Overview

| Checklist | When Created | How Created | Purpose | Gate |
|-----------|--------------|-------------|---------|------|
| `requirements.md` | After `/speckit.specify` | `/speckit.checklist requirements` | Validate spec quality | Pre-planning |
| `research-compliance.md` | During `/speckit.tasks` | Auto-generated | Verify research decisions | Pre-implementation |
| `implementation.md` | Optional, as needed | `/speckit.checklist implementation` | Domain-specific quality | Pre-merge |

## Checklist Lifecycle

```
/speckit.specify
       │
       ▼
┌──────────────────┐
│ requirements.md  │◄── /speckit.checklist requirements
│ (spec quality)   │
└────────┬─────────┘
         │ Gate: Must pass before /speckit.plan
         ▼
   /speckit.plan
       │
       ▼
   /speckit.tasks
       │
       ▼
┌──────────────────────┐
│ research-compliance  │◄── Auto-generated from research.md
│ (pattern/lib verify) │
└────────┬─────────────┘
         │ Gate: Must pass during /speckit.implement
         ▼
   /speckit.implement
       │
       ▼
   /speckit.verify ───► Automated pattern verification
       │
       ▼
┌──────────────────┐
│ implementation   │◄── Optional: /speckit.checklist implementation
│ (final quality)  │
└────────┬─────────┘
         │ Gate: Pre-merge review
         ▼
      Merge/Release
```

## 1. Requirements Checklist (`requirements.md`)

**Purpose**: "Unit tests for requirements" - validates that the specification is complete, clear, and ready for planning.

**When to create**: Immediately after `/speckit.specify` completes.

**How to create**:
```bash
/speckit.checklist requirements
```

**Standard items** (adapt based on feature):

```markdown
# Requirements Checklist: [FEATURE]

## Content Quality
- [ ] REQ001 - No implementation details in spec (languages, frameworks, APIs) [Quality]
- [ ] REQ002 - Focused on user value and business needs [Quality]
- [ ] REQ003 - Written for non-technical stakeholders [Quality]
- [ ] REQ004 - All mandatory sections completed [Completeness]

## Requirement Completeness
- [ ] REQ005 - No [NEEDS CLARIFICATION] markers remain [Completeness]
- [ ] REQ006 - Requirements are testable and unambiguous [Clarity]
- [ ] REQ007 - Success criteria are measurable [Measurability]
- [ ] REQ008 - Success criteria are technology-agnostic [Quality]
- [ ] REQ009 - All acceptance scenarios are defined [Coverage]
- [ ] REQ010 - Edge cases are identified [Coverage]
- [ ] REQ011 - Scope is clearly bounded [Clarity]
- [ ] REQ012 - Dependencies and assumptions identified [Completeness]

## Feature Readiness
- [ ] REQ013 - All functional requirements have clear acceptance criteria [Completeness]
- [ ] REQ014 - User scenarios cover primary flows [Coverage]
- [ ] REQ015 - Feature meets measurable outcomes defined in Success Criteria [Measurability]
- [ ] REQ016 - No implementation details leak into specification [Quality]
```

**Gate enforcement**: `/speckit.plan` should warn if `requirements.md` doesn't exist or has incomplete items.

## 2. Research Compliance Checklist (`research-compliance.md`)

**Purpose**: Verify implementation matches researched patterns, libraries, and decisions.

**When created**: Automatically during `/speckit.tasks` from `research.md`.

**How created**: Auto-generated by parsing research.md:
- Dependencies → DEP items
- Decisions → RC items
- Verification points → individual checklist items

**Example auto-generated content**:

```markdown
# Research Compliance Checklist: [FEATURE]

**Auto-generated from**: research.md
**Created**: [DATE]

## Dependency Verification

- [ ] DEP001 - Verify ddtrace >=4.0.0 is in pyproject.toml [Research §Dependencies]
- [ ] DEP002 - Verify datadog >=0.50.0 is in pyproject.toml [Research §Dependencies]

## Decision Compliance

### DEC-001: ddtrace LiteLLM Integration
- [ ] RC001 - ddtrace.patch(litellm=True) is used for instrumentation [Research §DEC-001]
- [ ] RC002 - No manual span creation for LLM calls [Research §DEC-001]

### DEC-002: Agentless Deployment Mode
- [ ] RC003 - LLMObs.enable(agentless_enabled=True) is configured [Research §DEC-002]
- [ ] RC004 - DD_API_KEY environment variable is documented [Research §DEC-002]
```

**Gate enforcement**: `/speckit.implement` step 2 gates on this checklist.

**Automated verification**: `/speckit.verify` can auto-check many of these items.

## 3. Implementation Checklist (`implementation.md`)

**Purpose**: Domain-specific quality gates for the specific feature being built.

**When to create**: Optional, when domain-specific checks are needed beyond standard research compliance.

**How to create**:
```bash
/speckit.checklist implementation
# Then describe the domain-specific checks needed
```

**Example domains and items**:

### API Feature
```markdown
## API Quality
- [ ] IMP001 - All endpoints have OpenAPI documentation [API]
- [ ] IMP002 - Error responses follow standard format [API]
- [ ] IMP003 - Rate limiting is implemented where specified [API]
- [ ] IMP004 - Authentication is required on protected endpoints [Security]
```

### UI Feature
```markdown
## UX Quality
- [ ] IMP001 - All interactive elements have hover states [UX]
- [ ] IMP002 - Loading states are defined for async operations [UX]
- [ ] IMP003 - Error states are user-friendly [UX]
- [ ] IMP004 - Mobile breakpoints are tested [Responsive]
```

### Data Feature
```markdown
## Data Quality
- [ ] IMP001 - Migrations are reversible [Data]
- [ ] IMP002 - Indexes are created for query patterns [Performance]
- [ ] IMP003 - Foreign keys have appropriate cascade rules [Data]
```

## Gate Enforcement Summary

| Command | Checks For | Behavior |
|---------|-----------|----------|
| `/speckit.plan` | `requirements.md` | Warn if missing/incomplete |
| `/speckit.implement` | All checklists in `checklists/` | **STOP** if any incomplete |
| `/speckit.verify` | `research-compliance.md` | Auto-verify where possible |

## Creating Custom Checklists

Use `/speckit.checklist` with a domain descriptor:

```bash
/speckit.checklist security   # Security-focused checklist
/speckit.checklist performance # Performance-focused checklist
/speckit.checklist accessibility # A11y-focused checklist
```

The command will:
1. Analyze spec.md, plan.md, and tasks.md
2. Generate domain-appropriate checklist items
3. Save to `checklists/[domain].md`

## Best Practices

1. **Create requirements.md early**: Do this immediately after spec is written, before planning
2. **Review research-compliance.md**: The auto-generated checklist should be reviewed for accuracy
3. **Don't over-checklist**: Only create implementation.md if there are domain-specific concerns
4. **Complete checklists as you go**: Check items off during implementation, not all at the end
5. **Use /speckit.verify**: Run automated verification to reduce manual checking burden
