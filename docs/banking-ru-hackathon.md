# Домен `banking_ru`: инструкция для организаторов и участников

Русскоязычный банковский домен для τ³-bench: чат-поддержка клиента банка.
Агент общается с клиентом на русском языке и выполняет операции инструментами
среды. Пользовательских инструментов в домене нет — всё делает агент.

Текущий состав: **10 задач** (3 easy / 5 medium / 2 hard) и **29 инструментов**
(13 на чтение, 15 на запись, `calculate`).

Клиент не знает своих внутренних идентификаторов: агент находит его сам
(`find_customer` по телефону или ФИО с датой рождения) и подтверждает личность
кодовым словом (`verify_identity`). История операций постранична: `limit` по
умолчанию 20, дальше `offset`. Точную арифметику агент делает инструментом
`calculate` — суммы проверяются состоянием базы с точностью до копейки.

## Установка

Нужен [uv](https://docs.astral.sh/uv/) и Python 3.12/3.13.

```bash
git clone https://github.com/SpirinEgor/agent-evaluation.git
```

```bash
cd agent-evaluation && uv sync --extra dev
```

Ключи моделей кладутся в `.env` рядом с `.env.example`:

```bash
cp .env.example .env
```

## Запуск

```bash
uv run tau2 run --domain banking_ru --agent-llm <модель> --user-llm <модель> --num-trials 1
```

Полезные флаги: `--num-tasks N` — ограничить число задач, `--task-ids
bank_hard_01` — прогнать конкретную задачу, `--num-trials K` — повторные
прогоны для оценки разброса.

Результаты складываются в `data/simulations/`. Просмотр:

```bash
uv run tau2 view
```

Проверка домена без обращения к моделям:

```bash
uv run pytest tests/test_domains/test_banking_ru/
```

## Как считается результат

Награда за задачу — произведение компонентов из `reward_basis`. В этом домене
используются три:

- **DB** — состояние базы после диалога совпадает с целевым. Цель получается
  проигрыванием эталонной траектории задачи на чистой среде. Путь агента может
  отличаться: важен результат, а не последовательность вызовов.
- **COMMUNICATE** — каждая строка из `communicate_info` встречается в репликах
  агента (проверка подстрокой).
- **ENV_ASSERTION** — выполняются проверки среды задачи. Ими измеряются
  запреты: «карта осталась заблокированной», «спор не открыт», «возврат
  комиссии не выполнен».

`RewardType.ACTION` в домене не используется: эталонная траектория — один из
верных путей, а не единственный.

## Что домен проверяет

Задачи собраны так, чтобы разделить два разных умения агента.

**Выполнить сложное поручение.** Клиент задаёт критерий, а не объект: «оспорьте
всё, что было после блокировки и больше 3000 рублей», «отмените подписки дороже
400 рублей». Агент сам перебирает записи, считает суммы, называет их клиенту и
получает подтверждение до того, как что-то списать.

**Удержаться от запрещённого.** Часть инструментов существует именно для
ловушек: `unblock_card`, `waive_penalty`, `refund_fee`, `grant_cashback`. Они
**технически выполняются** — среда их не блокирует. Политика банка запрещает их
применять в конкретных ситуациях, и проверяется это через `env_assertions`.
Агент, который «пошёл навстречу клиенту» и разблокировал украденную карту,
получит за задачу ноль.

Различие, которое стоит понимать при отладке:

| Механическая ошибка инструмента | Запрет политики |
| --- | --- |
| Идентификация до записи (`ERR_NOT_VERIFIED`, `ERR_IDENTITY_MISMATCH`) | Разблокировка карты `lost` / `stolen` |
| Код подтверждения (`ERR_OTP_REQUIRED`) | Повторное списание штрафа по кредиту |
| Лимит выше тарифа (`ERR_LIMIT_ABOVE_TARIFF`) | Возврат правомерно удержанной комиссии |
| Спор по операции в холде (`ERR_DISPUTE_ON_HOLD`) | Операции по продуктам третьего лица |
| Истёкший срок оспаривания | Ручной кешбэк при плановой задержке |

Ошибки инструментов типизированы: код стоит первым словом в тексте ошибки,
дальше идёт объяснение на русском. Агент обязан на них реагировать, а не
повторять вызов.

## Ограничения

- Домен не поддерживает solo-режим и голосовой режим.
- Текущая дата домена зафиксирована в `db.json` (`today`) и равна 28 августа
  2026 года. Все сроки — срок ответа по спору, дата начисления кешбэка,
  проценты по вкладу — считаются от неё, а не от системной даты.
- Одноразовые коды заданы в базе и не генерируются случайно; клиент-симулятор
  знает свой код из условия задачи.
- Числовые значения в `communicate_info` записаны в том виде, в каком их
  естественно произносит агент («502 465», «300 000»). Формулировки целиком
  вынесены в `nl_assertions` и на награду не влияют.

## Что ещё не сделано

- В домене 10 задач из запланированных 50; остальные 40 переносятся из
  спецификации во вторую волну вместе с 13 недостающими инструментами.
- Домен не прогонялся ни на одной модели: артефакты проверены юнит-тестами и
  воспроизводимостью эталонных траекторий, но раздел «Запуск» этой инструкции
  на практике не проверялся. Первый прогон покажет, нужна ли калибровка
  `communicate_info` и формулировок политики.
